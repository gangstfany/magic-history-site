# Magic History 独立仓库拆分方案

目标：保留现有网页外观与功能，让首页框架、账号、世界史、艺术史拥有各自GitHub仓库、提交历史、构建和部署。后续课程提交不修改首页或账号仓库，不自动部署首页。

## 拟建仓库

| 仓库 | 责任 |
| --- | --- |
| gangstfany/magic-history-site | 导航、首页外观、学科入口、通用框架、模块地址配置 |
| gangstfany/magic-history-auth | 登录/注册界面、认证服务封装、回调、账号样式、独立验证 |
| gangstfany/magic-history-apwh | 世界史地图、Today’s Pick数据与行为、工具栏、学习卡、因果链、商路、练习、内容构建及测试 |
| gangstfany/magic-history-art | 艺术史地图、作品资料及媒体、作品学习功能、独立构建及测试 |

每库默认main为日常分支，本地目录同名。若同名仓库已存在，先检查归属和内容，不覆盖。公开性以现有公开源码为参照；新的非公开资料不得自动纳入。

## 边界

首页只负责加载模块和模块选择，不直接读取课程内部DOM、全局变量或数据文件。课程专属工具栏与侧栏一起移动到课程模块；保持现在看到的页面组合与布局。模块通过带版本号、明确消息类型和来源校验的接口通知加载状态与高度。Today’s Pick由世界史模块提供展示数据及打开事件动作，首页保留展示位置。模块加载失败显示本模块的重试提示，首页导航继续可用。

账号仓库单独维护与发布，首页使用固定版本，课程发布不得自动更新账号版本。第一阶段保留既有Supabase项目和认证方式，不更换用户库、密钥或权限；对部署路径与回调地址的必要调整单独验证，跨来源不直接假定localStorage共享。上线前确认实际托管地址，若需Supabase控制台配置而不可访问，列出确切剩余操作。

独立仓库不等同于运行时绝对无故障；本次保障的是源码、提交、构建和发布边界，并通过稳定接口限制模块故障的影响。

## 迁移策略

世界史基线：course/apwh提交cd4401845ad5e688a0b33d930c61b8f3bcabb432，包含本轮全部内容整改和移除勘误入口。

艺术史采用实际最新课程实现并核对资源依赖，不以旧course/art-history分支替代正在维护的作品功能。迁移前检查所有艺术史工作区及分支状态，未提交内容不擅自覆盖或打包。

原magic-history仓库及现有部署保持可恢复，不删除、不强推、不先切正式入口。先完成四库本地版本、集成预览和验证，再初始化独立提交与远端推送；部署切换仅在新入口可用后进行。原仓库保留迁移说明与新仓库链接。

## 验收

1. 四个仓库各有自己的main、README、构建/验证命令和明确提交目的地。
2. 世界史独立运行，包含本轮完整功能；艺术史独立运行，资源加载正常。
3. 完整首页外观、登录入口和学科选择保持；从首页能进入两门课程。
4. 对世界史或艺术史做一次课程内容修改后，仅课程库发生文件变化；首页和账号库HEAD及文件校验保持一致。
5. 每库部署只读取自己的源码；不存在课程提交触发重建或覆盖首页的流水线。
6. 模块失败可重试，首页导航仍可用；账号登录及回调按实际部署来源验证。
7. 输出四个GitHub地址、完整预览地址及“改什么就提交哪个库”的操作表。

## 可选方式

推荐：四个独立仓库、模块独立构建和部署，首页固定接口加载。首次迁移工作量较大，但符合课程发布不触碰首页的目标。

较简单：四仓库，首页构建时复制课程代码。课程更新仍需重建发布首页，不满足本次主要目标。

继续单库分支：迁移工作最少，但提交目的地仍易混淆，不符合用户已明确的仓库要求。
